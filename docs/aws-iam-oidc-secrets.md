# AWS IAM, GitHub OIDC & Secrets Manager Configuration

## Purpose

This document explains where and how AWS authentication, database secrets, ECS/EC2 permissions, and GitHub Actions should be configured for the Coditude DevOps assessment.

The key principle is:

> Do not commit AWS credentials or production database passwords to the repository.

---

## 1. Configuration Overview

The intended security flow is:

```text
GitHub Actions
      |
      | GitHub OIDC
      v
AWS IAM Role
      |
      +----> CloudFormation
      +----> ECR
      +----> ECS
```

For database credentials:

```text
CloudFormation
      |
      v
AWS Secrets Manager
      |
      v
RDS PostgreSQL
```

For the applications:

```text
ECS Task Role  ---> Secrets Manager ---> DB credentials
EC2 Instance Role ---> Secrets Manager ---> DB credentials
```

---

## 2. What Must NOT Be Stored in GitHub

Do not commit any of the following:

- AWS access key ID
- AWS secret access key
- AWS console password
- Production RDS password
- Production database credentials
- ECR credentials
- ECS credentials

AWS authentication should use GitHub OIDC and IAM roles.

Production database credentials should use AWS Secrets Manager.

---

## 3. GitHub OIDC Configuration

### Where

AWS Console:

```text
IAM
  -> Identity providers
  -> Add provider
```

Configure:

```text
Provider type: OpenID Connect

Provider URL:
https://token.actions.githubusercontent.com

Audience:
sts.amazonaws.com
```

### Important

The repository already contains:

```text
infra/github-oidc.yaml
```

If this CloudFormation template creates the OIDC provider, do not create a duplicate provider manually. Use one approach consistently.

---

## 4. Create the GitHub Actions IAM Role

### Where

AWS Console:

```text
IAM
  -> Roles
  -> Create role
```

Example role name:

```text
GitHubActions-Coditude-DevOps
```

The role trust policy should:

1. Trust the GitHub OIDC provider.
2. Allow only the required GitHub repository.
3. Restrict the branch where appropriate.
4. Use least-privilege permissions.

The role is used by GitHub Actions to deploy AWS resources without storing long-lived AWS access keys.

---

## 5. Add the IAM Role ARN to GitHub

After creating the IAM role, AWS provides an ARN similar to:

```text
arn:aws:iam::<ACCOUNT_ID>:role/GitHubActions-Coditude-DevOps
```

### Where

GitHub:

```text
Repository
  -> Settings
  -> Secrets and variables
  -> Actions
  -> Secrets
  -> New repository secret
```

Create:

```text
Name:
AWS_ROLE_ARN

Value:
<GitHub Actions IAM role ARN>
```

---

## 6. GitHub Actions Configuration

The GitHub workflows should authenticate using the IAM role.

Example:

```yaml
- name: Configure AWS credentials
  uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
    aws-region: ap-south-1
```

This means:

```text
GitHub Actions
      |
      v
GitHub OIDC
      |
      v
AWS IAM Role
      |
      v
Temporary AWS credentials
```

No AWS access key or secret key needs to be stored in GitHub.

---

## 7. RDS Credentials — AWS Secrets Manager

### Repository file

```text
infra/database.yaml
```

The database stack should create an AWS Secrets Manager secret and generate the password.

Example:

```yaml
DBSecret:
  Type: AWS::SecretsManager::Secret
  Properties:
    Name: !Sub "${Environment}/postgres"
    GenerateSecretString:
      SecretStringTemplate: '{"username":"appuser"}'
      GenerateStringKey: password
      PasswordLength: 32
      ExcludeCharacters: '"@/\'
```

The important points are:

- The password is generated by AWS.
- The password is stored in Secrets Manager.
- The production password is not written in the repository.
- The application retrieves the secret at runtime.

---

## 8. ECS Access to the Database Secret

### Repository file

```text
infra/ecs.yaml
```

The backend ECS task role should have permission to retrieve the required secret.

Example permission:

```yaml
- Effect: Allow
  Action:
    - secretsmanager:GetSecretValue
  Resource: <DB secret ARN>
```

The ECS task definition can then inject values such as:

```text
DATABASE_USERNAME
DATABASE_PASSWORD
DATABASE_NAME
```

from Secrets Manager.

Flow:

```text
ECS Backend Task
      |
      v
ECS Task IAM Role
      |
      v
Secrets Manager
      |
      v
PostgreSQL credentials
```

---

## 9. EC2 Access to the Database Secret

### Repository file

```text
infra/ec2.yaml
```

For the non-containerized deployment, the EC2 instance should use an IAM instance role.

The role should have permission such as:

```json
{
  "Effect": "Allow",
  "Action": [
    "secretsmanager:GetSecretValue"
  ],
  "Resource": "<DB secret ARN>"
}
```

The EC2 application retrieves the database secret at runtime using the AWS SDK or AWS CLI.

Do not put the production password into:

- EC2 user-data
- AMI configuration
- application source code
- GitHub
- CloudFormation plaintext parameters

## 11. Application vs Infrastructure Deployment

### Application changes

Workflow:

```text
Code change
    |
    v
application.yml
    |
    v
Test
    |
    v
Build Docker images
    |
    v
Push to ECR
    |
    v
Deploy application
```

Application-only changes should not trigger a complete CloudFormation infrastructure deployment.

### Infrastructure changes

Workflow:

```text
Infrastructure change
    |
    v
infrastructure.yml
    |
    v
Validate CloudFormation
    |
    v
Deploy CloudFormation
```

This separation satisfies the requirement that application and infrastructure changes are handled independently.

---

## 12. Recommended Deployment Order

1. Configure GitHub OIDC and the GitHub Actions IAM role.
2. Deploy `infra/network.yaml`.
3. Deploy `infra/database.yaml`.
4. Deploy `infra/ecs.yaml` for the containerized implementation.
5. Deploy `infra/ec2.yaml` for the non-containerized implementation.
6. Deploy `infra/monitoring.yaml`.
7. Run GitHub Actions using the OIDC IAM role.

---

## 13. Security Checklist

- [ ] No AWS access keys committed to Git.
- [ ] No AWS secret keys committed to Git.
- [ ] No production DB password committed to Git.
- [ ] GitHub uses OIDC.
- [ ] GitHub IAM role is restricted to the required repository/branch.
- [ ] IAM permissions follow least privilege.
- [ ] RDS credentials are stored in Secrets Manager.
- [ ] ECS task role can read only the required secret.
- [ ] EC2 instance role can read only the required secret.
- [ ] RDS is private and not publicly accessible.
- [ ] Application and infrastructure workflows remain separate.
- [ ] Secrets are retrieved at runtime.

---

## 14. What You Actually Need to Configure Manually

You do **not** need to enter:

- AWS password
- AWS access key
- AWS secret key
- RDS production password
- ECR credentials
- ECS credentials

The main manual configuration is:

### AWS

```text
IAM
  -> GitHub OIDC provider
  -> GitHub Actions IAM role
```

### GitHub

```text
Repository
  -> Settings
  -> Secrets and variables
  -> Actions
  -> AWS_ROLE_ARN
```

### CloudFormation

```text
infra/database.yaml
  -> Secrets Manager
  -> RDS

infra/ecs.yaml
  -> ECS task role
  -> Secret injection

infra/ec2.yaml
  -> EC2 instance role
  -> Secret access
```

This gives the assessment a production-style authentication and secret-management model without putting long-lived credentials in source control.
